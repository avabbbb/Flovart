## Q1 轻面板的唯一挂载位置：宿主嵌入面还是画布内浮层？

现状：三个入口里「素材」已有真实实现（Workflow 侧栏页签），「任务」和「打开画布」尚未收敛；侧栏目前是画布内部的一等 UI，不是在浏览器任意页面都能唤出的小面板。todo 已记录要「确定唯一挂载位置（`/dock` 宿主嵌入面或画布内浮层），不新开第三个并列入口」。

需要 SOL 定的是**产品形态**，不是实现细节：

- 若选「`/dock` 宿主嵌入面」：用户在任意页面（甚至宿主 iframe 里）都能唤出，但这条路径要和 Workflow 保持同一份状态与同一组 operation，不能变成第二套状态投影；同时 P0 风险是宿主 iframe 可能直接禁用 File System Access API。
- 若选「画布内浮层」：复用成本最低，`LocalFolderBrowser` 已经是画布内组件；但「随手可用」的卖点弱，用户仍要先进入画布。

我的倾向：**先做画布内浮层把三个入口收敛成同一面板**（低成本、无新状态），把 `/dock` 留给「宿主集成 + 原生效果」阶段一起做。请确认是否接受这个顺序，还是认为 `/dock` 是这一轮必须出的一等形态。

## Q2 宿主 iframe 中目录授权被禁用时，降级入口走哪条？

`showDirectoryPicker` 在跨源 iframe 中可能被浏览器直接拒绝（未实测，属已知风险）。若成立，用户在 Studio 面板里点「选择文件夹」会直接失败。

可选的降级：

1. 退回既有「导入副本」路径（`ingestWorkflowMedia`），并在 UI 明示这次是复制而非引用；
2. 引导用户到独立浏览器页 / 桌面端（Tauri 本地服务）完成目录授权；
3. 只做提示，不提供降级，等 `/dock` 或原生效果阶段再解决。

需要 SOL 判断的是**是否接受「同一台机器上两种素材语义并存」**，以及如果接受，要不要在节点上显式区分「引用」与「副本」（现在 `sourceType` 已经区分 `assetLibrary` / `localFolder`，但没有面向用户的标记）。

## Q3 优先级：先做导出引用失效检测，还是先做助手给文件夹路径？

两条都在 todo 里，都要动不同层：

- **导出引用失效检测**：纯前端 + 导出路径，成本低，堵的是一个**真实存在**的坑——原文件被移动/重命名后导出会失败但当前没有显式拦截，用户可能拿到内容缺帧的结果。我判断这是眼下最该先补的一项。
- **助手直接给文件夹路径**：需要动 Rust `tiny_http` 本地服务新增**受限目录读取接口**，要做路径校验、授权范围、最小权限设计；这是新增攻击面，设计成本明显更高。

请确认优先级，或给出第三条路（例如两者都不做，先收敛面板与入口）。

## Q4 `local-folder:` 引用在跨机器 / 打包分发 / 协作场景下的预期行为？

引用语义的代价已经在 ADR 0071 记录：原文件移走、换机器、把工程发给别人，节点都会读不到。现在 `LocalFolderError` 会把原因原样透出（权限失效 / 原文件被移动），用户可重新定位，但**没有任何「转为副本」的显式动作**——一旦要分享工程，用户没有正规出路。

需要 SOL 定：

- 工程打包/分发时是否**强制**把引用转成副本（还是仅在导出时检查）？
- 是否提供一个显式的「转换为副本」操作，让用户在有预期分享需求时固化素材？
- 协作/云同步场景是否明确**不支持**引用语义（我倾向明确写不支持，避免宣传过度）？

## Q5 是否把 `insertSharedMedia` 与 `insertLocalFolderEntries` 合并成单一素材入口？

现状：两条插入路径都收敛到了 `commitMediaNodes`（一次 Draft ChangeSet），但入口函数仍是两个。AGENTS.md 要求「抽象与接口在第二个真实使用场景出现时再提取」——现在第二个场景已经出现，所以这是一个真实的合并候选。

反面理由：合并后需要一个「素材来源描述」类型，可能引入一层只为转发而存在的抽象；且两条路径的失败处理语义不同（副本导入可能部分成功，引用插入失败需要提示重新定位）。

请 SOL 给一个判断：**合并**（单一素材入口，来源作为参数）、**保持两条**（各自处理失败语义），还是**只统一 UI 入口、底层保持两个函数**（我倾向这一条）。

## Q6 画布平移/缩放按帧写 viewport 要不要在本轮一起改？

画布三项只改了节点拖动与缩放；视口平移/缩放仍每帧写 viewport。改动形状与已完成的拖动收敛**高度相似**（预览 + 松手/手势结束提交），预期能复用同一套 `InteractionPreview` 机制，但需要先实测确认现在是否真的有掉帧或存储写入压力——todo 里「大图性能（剩余）」明确要求「按实际性能问题优化」。

请 SOL 判断：**先实测再决定**（我倾向），还是**直接按一致性顺手改掉**。

## Q7 本轮画布改动的回归风险，需要什么样的确认标准？

视口裁剪 + 拖动提交时机是画布核心交互，测试全绿只证明 jsdom 下的契约，真实大项目里的掉帧、连线和批组栈跟随、内存峰值都**未实测**。pending-test 已经写了待用户实测项。

请 SOL 明确：这一轮是要**用户自己在真实项目里过一遍**再更新 features，还是需要补一组真实浏览器基准（固定素材 + 固定浏览器版本 + 记录口径）才算过？如果要基准，阈值定在哪（主设计第 6 节给了方法，但阈值仍是建议目标）。
